# Webbys Sales and Promotion Analytics Design

## Goal

Add a read-only Sales module so the administrator can inspect existing sale records and understand sales results, including the difference between sales attributed to a promotion and sales that merely occurred during its date range.

## User decisions

- The user specified: “no, este usuario no quiero que registre ventas, solo vea los registros”
- The user selected: “si la opcion 1”
- The user approved the design direction: “hazlo”
- The user clarified the initial Sales date range: “oye solo una duda muestra las ventas e ingresos pero no sale de que fecha o rangos de fechas al inicio, ademas quisiera que ahi pudiera elejir el rango de fecha, por defecto debe ser del dia”

## Approved scope

- Add a protected `/ventas/` route linked from the existing authenticated navigation.
- Show a searchable/filterable, mobile-first sales register and a sale detail view.
- Filter records by date range, employee, product, service, and promotion.
- Show the active date range above the Sales summary. On initial entry, both range boundaries are the current local date; the user can change either boundary with the existing collapsible month-calendar popover.
- The selected inclusive date range applies consistently to the Sales list, summary, daily trend, item/employee breakdowns, and promotion reporting.
- Show gross sales, discounts, net sales, sale count, and average ticket for the selected records; chart daily net sales and provide read-only breakdowns for products, services, employees, and promotions.
- Keep promotion attribution explicit and distinct from sales that only occurred during a promotion's date range. Date overlap is contextual reporting, not proof of causality.
- Extend only the generated demonstration records and their types with the snapshots/IDs required for these views. Reuse the current sales data flow rather than adding a writable sales collection.

## Non-goals and constraints

- Do not add sale creation, editing, cancellation, refunds, or any other sales mutation UI.
- Do not decrement or otherwise mutate product stock.
- Do not claim live business results, causal lift, profit, or return on investment from generated demonstration records.
- Do not create a backend, remote API, payment integration, or database.
- An explicitly attributed sale requires an explicit promotion ID in its record; date overlap alone must never be labeled attributed.

## Data and interaction design

Sales remain generated by the existing demo-data source and are provided to the page as read-only records. Each newly generated record carries a stable ID and timestamp, item snapshots with catalog identity/kind, quantity and unit-price snapshot, employee identity/name snapshot, payment method, operation status, and an optional explicitly attributed promotion ID/name snapshot. Transaction records retain gross, discount, and net totals. New metadata fields remain optional in shared types to preserve compatibility with existing dashboard fixtures and records. Summary values are derived from the records, not separately stored totals.

The sales list supports text search and the five specified filters. Opening a record shows its item and transaction snapshots. Period summaries derive gross, discounts, and net from included records. Promotion reporting presents two separate counts/amounts: explicitly attributed records and records occurring within the promotion's date window. Labels and descriptions state that the latter is temporal overlap only.

Reuse `AdminGate`, `AdminShell`, `Dropdown`, existing page/list/detail conventions, and established dashboard sales calculations where they fit. Keep calculations in pure service functions and cover them with deterministic tests.

## Verification

- Test that sales summaries, filters, item totals, and promotion-attribution/date-overlap classifications are deterministic.
- Test that date overlap never creates promotion attribution and that invalid/out-of-range filters do not mutate data.
- Test the read-only page: search, each filter, record detail, empty state, and no sale-writing or stock-mutation controls.
- Run focused tests, the full Vitest suite, `npm run check`, and `npm run build`.
